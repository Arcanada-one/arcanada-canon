# 1. Иерархия пространств

Основную структурную иерархию лучше сделать такой:

```
Universe
└── Galaxy
    └── Space
        └── Project
            └── Module
```

`Module` можно оставить необязательным.

Например:

```
Universe: Arcanada
└── Galaxy: Core Infrastructure
    └── Space: Agent Execution
        └── Project: Muneral Arcana
            └── Module: Work Graph Resolver
```

Но персональный пользовательский уровень я бы **не помещал внутрь этого дерева**.

Пользователь может одновременно работать в нескольких проектах, пространствах и даже вселенных. Поэтому персональный контекст должен быть overlay — дополнительным слоем, накладываемым после разрешения структурной иерархии.

Получается три вида контекста.

### Структурный контекст

```
Universe → Galaxy → Space → Project → Module
```

### Контекст субъекта

```
Organization → Team → User → Agent
```

### Контекст исполнения

```
Work Item → Phase → Current Action
```

Финальный порядок сборки:

```
Structural Context
+ Authorized Actor Overlays
+ Work Item Context
+ Phase Context
= Resolved Context
```

При этом нижние уровни могут специализировать верхние, но не должны иметь возможность отменять фундаментальные запреты и обязательства вселенной.

# 2. Не один Markdown, а три слоя представления

Чтобы одновременно сохранить весь исходный смысл и минимизировать контекст агента, нужно разделить систему на три слоя.

## Слой 1. Source Canon

Полные исходные документы:

- могут быть написаны на русском, английском или другом языке;
- содержат объяснения, мотивацию, примеры;
- сохраняют историю возникновения идеи;
- могут быть достаточно подробными;
- редактируются человеком или агентом через Git;
- являются главным источником истины.

Например:

```
universes/arcanada/policies/external-actions-provenance.md
```

## Слой 2. Normalized Canon

Нормализованное представление:

- всегда на английском;
- разбито на атомарные утверждения;
- использует контролируемые формулировки `MUST`, `MUST NOT`, `SHOULD`, `MAY`, `DEFINES`;
- не содержит литературной воды;
- каждое утверждение связано с исходным артефактом;
- проверено валидатором;
- имеет стабильный идентификатор.

Пример:

```
MUST record every external side effect in the Provenance Journal.
MUST include actor, intent, target, authorization, result, timestamp, and rollback reference.
MUST NOT execute an irreversible external action without explicit authorization.
```

## Слой 3. Resolved Runtime Context

Контекст, фактически передаваемый агенту:

- содержит унаследованные правила всех уровней;
- учитывает пользователя, проект, Work Item и текущую фазу;
- удаляет дубликаты;
- разрешает допустимые переопределения;
- выбирает только активные для задачи условные правила;
- укладывается в заданный token budget;
- всегда воспроизводим;
- имеет digest и immutable snapshot.

Именно этот слой становится частью Knowledge Contract или Prompt Assembly.

# 3. Компиляция не должна происходить заново при каждом запуске

Это принципиально важно.

Не стоит при каждом вызове агента отдавать модели десятки Markdown-файлов и просить:

> 
> Переведи, объедини, убери дубли и сократи без потери смысла.
> 
> 
> 

Такой результат будет:

- недетерминированным;
- невоспроизводимым;
- потенциально противоречивым;
- постепенно теряющим смысл;
- дорогим по токенам;
- сложным для аудита.

LLM может **предлагать** перевод, нормализацию и сжатие во время изменения Canon, но результат должен пройти maker-checker, попасть в Git и стать версионированным артефактом.

Во время исполнения используется уже утверждённый Normalized Canon. Runtime Resolver только детерминированно:

1. выбирает нужные области;
2. применяет наследование;
3. разрешает overlays;
4. фильтрует условные правила;
5. собирает компактный bundle.

То есть интеллектуальная семантическая работа происходит при обновлении Canon, а не при каждом запуске агента.

# 4. Что именно хранить в Canon Arcana

Не следует превращать Canon Arcana в свалку всех знаний Арканады. Там должны находиться только **авторитетные и канонические утверждения**.

Основные типы артефактов:

- `charter` — цель, миссия, роль и границы пространства;
- `principle` — принцип принятия решений;
- `policy` — обязательная политика;
- `rule` — конкретное операционное правило;
- `definition` — каноническое определение термина;
- `decision` — принятое архитектурное или организационное решение;
- `constraint` — ограничение;
- `exception` — явно разрешённое исключение;
- `assumption` — допущение, истинность которого может измениться;
- `canonical-knowledge` — базовое знание, которое должно считаться общепринятым внутри области.

Роли, Skills, Blueprints и Capability Descriptions лучше продолжать хранить в отдельном репозитории Knowledge Artifacts. Canon Arcana может ссылаться на них, но не должен их дублировать.

Также в Canon Arcana не должны храниться:

- диалоги — это Dialogue Arcana;
- история запусков — Run Ledger Arcana;
- состояние задач — Muneral Arcana;
- пароли и ключи — Custodium Arcana;
- большие исследования и документы — они индексируются Scrutator;
- временные размышления, ещё не признанные каноном.

Для новых мыслей нужен отдельный статус и каталог `proposals`.

Жизненный цикл:

```
idea → draft → reviewed → active → deprecated → superseded
```

Только `active`-артефакты участвуют в production-компиляции.

# 6. Формат `index.md` — устав пространства

У каждого Universe, Galaxy, Space, Project и Module должен быть обязательный `index.md`.

```
---
id: arcana.scope.project.muneral
kind: charter
scope_type: project
parent: arcana.scope.space.agent-execution
status: active
version: 1.0.0
source_language: ru
owner: arcanada
visibility: internal
imports:
  - arcana.pack.provenance
  - arcana.pack.external-actions
---

# Muneral Arcana

## Purpose

Почему это пространство существует.

## Mission

Какую постоянную функцию оно выполняет.

## Role in Parent Scope

Какую роль проект выполняет внутри родительского пространства.

## Desired Outcomes

Как должно выглядеть успешное состояние.

## Boundaries

Что относится и что не относится к этому пространству.

## Principles

Ключевые принципы принятия решений.

## Non-negotiables

Что запрещено нарушать.

## Success Criteria

По каким признакам можно понять, что пространство выполняет свою роль.
```

Таким образом, `index.md` отвечает на вопрос **«что это за пространство»**, а отдельные файлы — **«какие именно утверждения и правила в нём действуют»**.

# 7. Формат атомарного артефакта

Один файл желательно посвящать одной смысловой единице.

```
---
id: arcana.policy.external-actions.provenance
kind: policy
scope: universe/arcanada
status: active
version: 1.0.0
strength: must
overridable: false
activation: always
source_language: ru
canonical_language: en
owner: pavel-valentov
visibility: internal
supersedes: []
related:
  - arcana.definition.external-action
  - arcana.system.run-ledger
---

# Журналирование внешних действий

## Source statement

Любое действие агента, изменяющее внешний мир, должно быть
зафиксировано в журнале происхождения и действий.

## Rationale

Без записи невозможно достоверно восстановить, кто, зачем,
на основании какого разрешения и с каким результатом выполнил действие.

## Required meaning

- Внешнее действие нельзя выполнить анонимно.
- Должны быть зафиксированы намерение и авторизация.
- Должны быть зафиксированы результат и возможность отката.
- Требование распространяется на агентов и оркестраторы.

## Counterexamples

- Агент выполнил `git push`, но записал только факт успешного завершения.
- Агент изменил запись в базе данных без ссылки на Work Item.
```

Разделы `Required meaning` и `Counterexamples` особенно важны: они дают валидатору возможность проверять не только похожесть текста, но и сохранение границ смысла.

# 8. Правила наследования

Простого принципа «нижний уровень всегда побеждает верхний» недостаточно. Иначе пользователь или проект сможет случайно отменить безопасность всей Вселенной.

Нужны разные правила для разных типов утверждений.

### Hard policies и constraints

Наследуются и накапливаются. Нижний уровень может сделать их строже, но не слабее.

```
Universe: External actions require authorization.
Project: Git operations require authorization through an approved adapter.
```

Оба правила остаются активными.

### Defaults

Ближайшее более специфичное значение побеждает.

```
Universe default language: English
User preferred dialogue language: Russian
```

Пользовательский overlay может изменить язык диалога, но не обязательный язык скомпилированного Canon.

### Definitions

Ближайшее определение может уточнить родительское, только если родительское определение не помечено как locked.

### Permissions

Запрет должен иметь приоритет над разрешением:

```
deny > allow
```

### Отключение и замена

Отсутствие правила в дочерней папке не отменяет родительское правило.

Для отмены или замены нужны явные конструкции:

```
supersedes:
  - previous.policy.id
```

или:

```
waiver:
  policy: policy.id
  authorized_by: authority.id
  expires_at: 2026-12-31
```

### Конфликты

Неразрешённый конфликт должен останавливать компиляцию.

Нельзя молча выбрать один из вариантов, потому что тогда агент получит контекст, который никто сознательно не утверждал.

# 9. Три режима включения знаний

Чтобы не засыпать окно контекста, каждому артефакту нужен режим активации.

## `always`

Всегда включается:

- purpose;
- mission;
- базовые определения;
- фундаментальные запреты;
- безопасность;
- provenance;
- общие правила Knowledge Contract.

## `conditional`

Включается, когда совпало условие:

```
activation:
  mode: conditional
  when:
    tools:
      - git
      - github
    actions:
      - write
      - merge
```

Например, правила GitHub не нужны агенту, который только анализирует текст.

## `retrieval`

Не помещается в основной контекст. Доступно через Scrutator:

- расширенные объяснения;
- исследования;
- примеры;
- история решений;
- доказательства;
- длинные инструкции;
- редкие edge cases.

Поэтому «полный контекст» должен означать не «все документы загружены в prompt», а:

> 
> Все обязательные смыслы присутствуют, а дополнительные знания доступны по стабильным ссылкам и могут быть извлечены при необходимости.
> 
> 
>

# 10. Компилятор Canon Arcana

Для существующего Rust CLI логично добавить отдельный crate или командную группу:

```
arcana canon lint
arcana canon normalize
arcana canon compile
arcana canon resolve
arcana canon explain
arcana canon diff
```

### `lint`

Проверяет:

- frontmatter;
- типы;
- IDs;
- parent relations;
- битые ссылки;
- циклы;
- неизвестные imports;
- статусы;
- обязательные разделы.

### `normalize`

Создаёт или обновляет атомарную английскую форму. Может использовать LLM, но результат не становится активным без проверки.

### `compile`

# 12. Как защищаться от потери смысла

Полностью гарантировать «сжатие свободного текста без потери смысла» одной инструкцией LLM невозможно. Но можно построить процесс, при котором непроверенная потеря смысла блокирует публикацию.

Для этого нужны:

1. **Атомарность:** одна самостоятельная мысль — один идентифицируемый clause.
2. **Source mapping:** каждый compact clause хранит ссылки на исходные утверждения.
3. **Coverage:** ни одно обязательное утверждение не может исчезнуть без явной причины.
4. **Двусторонняя проверка:** compact-версия должна следовать из исходника и не должна добавлять более сильного утверждения, которого в исходнике не было.
5. **Проверка отрицаний и исключений:** `not`, `unless`, `only`, `at least`, `before`, `after` нельзя терять при сжатии.
6. **Контрпримеры:** проверяющий агент пытается найти трактовку, нарушающую исходный смысл.
7. **Semantic diff:** изменение Canon показывает, какие обязанности, разрешения или ограничения реально поменялись.
8. **Maker-checker:** один агент формулирует, второй атакует результат и ищет потерянные границы.
9. **Human gate:** фундаментальные политики уровня Universe и Galaxy требуют утверждения владельцем.

Компактный контекст может не содержать полные source IDs, чтобы не расходовать токены. Позиции текста связываются с источниками через внешний manifest.

## 2. Bundle не равен prompt

Я ввёл три отдельных понятия.

### Canon Bundle

Полный скомпилированный пакет scope или protocol:

- все clauses;
- все уровни представлений;
- applicability indexes;
- graph links;
- source maps;
- manifests;
- retrieval metadata.

Он может быть большим — десятки или сотни килобайт. Но **он никогда не передаётся модели целиком автоматически**.

### Context Capsule

Небольшой пакет, выбранный для конкретной задачи:

```
Canon Kernel
+ mandatory task rules
+ project/module constraints
+ capability summary
+ Knowledge Contract instance
+ selected guidance
+ retrieval handles
```

Именно Capsule попадает в initial prompt.

### Context Snapshot

Неизменяемая запись:

- из каких releases собран Capsule;
- какие clauses выбраны;
- какие representations использованы;
- какие правила обеспечиваются runtime guards;
- какая версия selector, classifier, graph и reranker применялась.

Это позволяет точно воспроизвести контекст агента спустя время.

Исследования long-context систем подтверждают, что большое окно само по себе не решает задачу: при избытке материала падает плотность полезного сигнала, а информация в середине длинного контекста может использоваться хуже. Поэтому архитектура строится вокруг минимального initial context и progressive disclosure. [Anthropic+1](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

## 3. Сложность нельзя определять одним числом

Предложение использовать число графовых связей разумно как один из сигналов, но **не как единственный показатель**.

Например:

- удаление production-базы может быть интеллектуально простой задачей, но крайне рискованной;
- научное исследование может быть сложным, но не затрагивать внешний мир;
- популярный термин может иметь тысячи графовых связей, хотя задача касается одного локального свойства.

Поэтому Context Planner оценивает четыре независимые оси:

```
C — Cognitive Complexity
G — Graph / Scope Breadth
R — Operational Risk
U — Context Uncertainty
```

После этого определяется `Context Demand Class`:

```
D0 — atomic/local
D1 — local project task
D2 — cross-component
D3 — cross-scope or high-risk
D4 — strategic/foundation/universe
```

Формула консервативная:

```
D = max(
    demand_from_C,
    demand_from_G,
    risk_floor(R),
    uncertainty_floor(U),
    authority_floor,
    explicit_binding_floor
)
```

То есть простая production-операция всё равно получит высокий класс из-за `risk floor`.

Количество графовых связей считается только внутри **task-induced subgraph**:

- затронутые компоненты;
- типы связей;
- число переходов между модулями и проектами;
- количество пересечённых scope boundaries;
- длина действительно релевантных цепочек;
- число authority domains.

Высокая степень одного центрального узла не должна автоматически увеличивать prompt.

Для локальных вопросов используется local graph search, для Galaxy/Universe-wide вопросов — community/global search. Такой принцип соответствует разделению local и global retrieval в GraphRAG. [Microsoft на GitHub+2Microsoft на GitHub+2](https://microsoft.github.io/graphrag/query/local_search/)

## 7. Не каждая новая идея должна становиться Universe Canon

Для твоих постоянно возникающих идей введён отдельный, но встроенный жизненный цикл:

```
Idea
→ Triage
→ Enrichment
→ Proposal / RFC
→ Review
→ Decision
→ Canon Artifact
```

### Raw Idea

Хранится в `Idea Ledger`:

- исходный текст без принудительного редактирования;
- автор;
- время;
- источник — диалог, Work Item, проект;
- предполагаемый scope;
- связанные идеи;
- provenance.

Она индексируется Scrutator в namespace `ideas`, но имеет:

```
runtime_eligible: false
authority: unverified
```

### Proposal / RFC

Когда идея созрела, она материализуется как Markdown в Git:

```
proposals/2026/PROP-0042-counterexample-first-research.md
```

### Canon

Только после review и решения из Proposal создаётся действующее правило, definition, protocol или principle.

Такой подход сохраняет каждую мысль, но не превращает production-контекст агентов в поток непроверенных гипотез. Использование отдельной стадии Markdown RFC перед активацией значимых изменений соответствует зрелым инженерным процессам, например Rust RFC. [GitHub](https://github.com/rust-lang/rfcs)

```
Parent Meaning Ledger
+ Parent normalized clauses
+ Parent source maps
+ Conflict and authority metadata
```

Иначе любая небольшая потеря смысла на уровне Universe попадала бы в Galaxy, потом усиливалась в Space, затем в Project — возникал бы каскад semantic drift.

Сжатые `kernel.en.md` и `micro.jsonl` являются выходными runtime-представлениями, но не заменяют полный смысловой реестр при следующей компиляции.

## 2. Пользовательские каноны компилируются отдельно

Для них предусмотрен `ActorOverlayRelease`:

```
Organization Canon
Team Canon
User Canon
Agent Canon
```

Каждый overlay содержит только собственные пользовательские правила и предпочтения. В него не копируется Universe, Galaxy или Project Canon.

При запуске агента выполняется детерминированная сборка:

```
Effective Scope Release
+ Organization Overlay
+ Team Overlay
+ User Overlay
+ Agent Overlay
+ Knowledge Contract instance
= Context Plan
```

То есть появление нового пользователя не заставляет перекомпилировать все проекты.

Locked-политики верхнего уровня имеют приоритет. Например, пользователь может изменить предпочитаемый стиль ответа, но не может отменить обязательное журналирование внешних действий.

# 3. Canon Consilium

Для стандартной production-компиляции принят профиль:

```
3 candidate compilers
+ 2 auditors
+ Canon Consigliere
+ Independent Release Verifier
```

Это не семь агентов, которые бесконтрольно разговаривают друг с другом. Это управляемый конвейер с разделением ответственности.

Исследования действительно показывают, что несколько независимых кандидатов и много-модельная агрегация могут улучшать результат. Но они также показывают, что случайное смешивание более слабых моделей способно ухудшить итог, а эффективность debate зависит от сложности, структуры взаимодействия и качества участников. Поэтому в ТЗ введены одновременно model diversity и обязательный quality floor. [arXiv+3arXiv+3arXiv+3](https://arxiv.org/abs/2305.14325)

## Три независимых компилятора

### Semantic Conservator

Главная задача — не потерять ни одного смысла.

Он:

- внимательно работает с оригинальным языком;
- сохраняет субъект, объект и область действия;
- сохраняет отрицания, условия и исключения;
- не жертвует полнотой ради краткости;
- помечает утверждения `non_compressible`, если их нельзя безопасно сократить.

### Normative Architect

Преобразует знания в контролируемый нормативный английский:

```
MUST
MUST NOT
SHOULD
SHOULD NOT
MAY
DEFINES
PREFERS
```

Он разделяет:

- определения;
- обязанности;
- запреты;
- разрешения;
- rationale;
- примеры;
- applicability.

Также он проверяет правильность уровня абстракции.

### Compression Engineer

Ищет минимальную формулировку, но только при фиксированном смысловом покрытии.

Он выпускает:

- `micro`;
- `standard`;
- `full`;
- `kernel`;
- task-addressable capsules.

Если смысл нельзя сохранить при сокращении, он обязан отказаться от сокращения.

---

## Два независимых аудитора

### Scope & Inheritance Auditor

Проверяет:

- правильный ли выбран уровень;
- не попал ли Blueprint или Skill в structural Canon;
- не потеряно ли унаследованное правило;
- не ослаблена ли locked-политика;
- не выдан ли parent clause за локальный;
- законны ли waiver и supersession;
- правильно ли подключён Knowledge Contract package.

### Adversarial Fidelity Auditor

Целенаправленно атакует результаты компиляторов:

- ищет пропущенные смыслы;
- ищет придуманные обязанности;
- строит контрпримеры;
- проверяет `unless`, `only`, `before`, `after`;
- проверяет числа, лимиты и единицы;
- ищет замену `MUST` на `SHOULD`;
- проверяет перевод;
- выявляет красивую, но семантически неверную упаковку.

# 4. Canon Consigliere

Consigliere не выбирает целиком «лучший документ».

Он принимает решение **по каждому смыслу или группе эквивалентных смыслов**:

```
Meaning Unit 001
├── Candidate A wording
├── Candidate B wording
├── Candidate C wording
├── Scope audit
├── Fidelity objections
└── Consigliere decision
```

Для одного смысла он может выбрать формулировку модели A, для другого — модели B, а для третьего синтезировать новую формулировку из поддержанных источником элементов.

Но синтез ограничен:

```
Final clause MUST have source mapping.
Final clause MUST preserve scope and authority.
Final clause MUST preserve modality and polarity.
Final clause MUST preserve conditions and exceptions.
Final clause MUST NOT add unsupported normative meaning.
Final clause MUST have no unresolved blocker.
```

### Важное отличие от большинства голосов

Если три модели одинаково ошиблись, это не делает ошибку каноном.

В ТЗ явно записано:

> 
> Согласие моделей — это сигнал, но не источник нормативной истины. Источником истины остаются исходные утверждения и их authority.
> 
> 
>

# 5. Независимость кандидатов и защита от влияния судьи

Первый проход выполняется вслепую:

1. Компиляторы не видят ответы друг друга.
2. Результаты получают анонимные идентификаторы A, B, C.
3. Аудиторы не знают, какая модель подготовила вариант.
4. Порядок вариантов рандомизируется.
5. Для critical clauses сравнение повторяется с обратным порядком.
6. Только после независимых проходов Consigliere получает весь набор evidence.
7. По умолчанию разрешён один targeted revision round.
8. Бесконечная дискуссия запрещена.

Это важно, потому что LLM-судьи демонстрируют position, verbosity и self-preference biases: изменение порядка вариантов способно изменить оценку. Поэтому простой единичный вызов «выбери лучший ответ» для Canon недостаточен. [arXiv+1](https://arxiv.org/abs/2305.17926)

# 6. Meaning Ledger и Objection Ledger

## Meaning Ledger

До сжатия source разбивается на атомарные единицы:

```
id: smu.external-actions.001
subject: agent
predicate: record
object: external_side_effect
modality: must
polarity: positive
conditions:
  - action.has_external_side_effect == true
temporal_order:
  - record.authorization BEFORE execute.action
criticality: critical
source_fragment_refs:
  - artifact: canon.policy.external-actions.provenance
    anchor: required-meaning-1
```

Для каждого смысла отдельно хранятся:

- субъект;
- действие;
- объект;
- модальность;
- отрицание;
- условия;
- исключения;
- численные ограничения;
- последовательность;
- authority;
- scope;
- source anchors.

Именно этот Ledger наследует следующий уровень.

## Objection Ledger

Каждая претензия аудитора становится структурированной сущностью:

```
kind: lost_exception
severity: blocker
target_candidate: candidate-B
target_clause: clause.temp.17
source_meaning_ids:
  - smu.004
evidence: >
  The source permits execution only after explicit approval.
suggested_resolution: Restore the approval condition.
status: open
```

Ни один release не может перейти в `ready`, пока остаётся открытый blocker.

Для проверки сохранения смысла в ТЗ предусмотрена комбинация entailment-, QA- и adversarial-проверок. Исследования factual consistency показывают, что NLI и question-answering дают разные и взаимодополняющие сигналы, поэтому использовать только embedding similarity недостаточно. [arXiv+1](https://arxiv.org/abs/2111.09525)

# 7. Компактный Canon больше не считается одним файлом

Пытаться ужать всю Вселенную и весь проект в один Markdown небезопасно. Поэтому Consilium выпускает набор представлений:

```
normalized.full.jsonl
scope-summary.en.md
kernel.en.md
micro.jsonl
standard.jsonl
capsule-catalog.json
retrieval-manifest.json
non-compressible.json
```

Оптимизационная задача сформулирована так:

```
minimize(runtime_tokens)

subject to:

critical_meaning_recall = 1.0
unsupported_normative_meanings = 0
scope_preservation = required threshold
modality_preservation = required threshold
condition_exception_preservation = required threshold
```

Если всё не помещается в один текст, смысл не удаляется. Он переносится в deterministic task capsule, который Context Planner подключает по applicability.

# 8. Model Portfolio

ТЗ не требует использовать пять случайных моделей.

`CouncilProfile` задаёт:

```
minimum_distinct_model_families: 3
minimum_distinct_providers: 2
maximum_candidate_seats_per_family: 2
chair_must_not_be_candidate_author: true
minimum_quality_tier: canon-compiler-approved
```

Модели выбираются через:

```
Model Atlas
→ approved benchmark tier
→ Model Connector
→ Council seat
```

При этом:

- слабая модель не получает равный вес только ради diversity;
- confidential source можно отправлять только разрешённым private/local providers;
- хотя бы один auditor должен использовать другую model family;
- модель Consigliere не должна быть автором candidate;
- отсутствие минимального состава блокирует production publication.

# 9. Перекомпиляция и зависимость уровней

Введён dirty dependency graph.

Перекомпиляция запускается только при изменении:

- локального source;
- parent release;
- подключённого package;
- binding;
- waiver;
- prompt bundle;
- model portfolio;
- compiler version;
- validation policy.

Default cadence:

```
Universe / Foundation Protocol:
    weekly when dirty
    + manual
    + emergency

Galaxy / Space / Project / Module:
    nightly when dirty
    + manual

Actor overlays:
    debounced preview
    + daily or explicit production compile
```

Если входные digests не изменились, возвращается cached release. После публикации parent release потомки получают `stale_due_to_parent` и перестраиваются в топологическом порядке.

# 10. Эволюция самого компилятора

Это отдельный объект:

```
CompilerRelease
```

Он фиксирует:

- compiler binary digest;
- Prompt Bundle digest;
- CouncilProfiles;
- rubrics;
- JSON Schemas;
- model portfolio;
- evaluator versions;
- Golden Canon Set;
- совместимость.

Жизненный цикл:

```
draft
→ golden-evaluated
→ shadow-recompile
→ human-diff-reviewed
→ canary-authorities
→ active
→ superseded / rolled_back
```

Если source не менялся, но новый компилятор внезапно изменил обязательный смысл, такая разница выделяется отдельно как `compiler-originated semantic change` и блокирует автоматическое продвижение.

Также в ТЗ честно зафиксировано: если внешний provider не закрепляет точные weights и runtime модели, нельзя гарантировать bit-for-bit повторение inference. Поэтому главным воспроизводимым объектом является уже опубликованный immutable bundle плюс полный Compilation Ledger.

# 11. Где хранить ТЗ и промпты

Их можно хранить в том же Git-репозитории, но с жёстким разделением:

```
/canon        → active runtime source
/governance   → правила управления Canon
/compiler     → prompts, profiles, rubrics, schemas
/docs         → ТЗ, архитектура, runbooks
/proposals    → изменения
/tests        → goldens и mutations
```

В `canon.source.yaml` явно задаётся:

```
- path: /canon
  runtime_eligible: true

- path: /compiler
  runtime_eligible: false

- path: /docs
  runtime_eligible: false
```

Поэтому само ТЗ и промпты могут эволюционировать рядом с Canon, но случайно не попадут в prompt обычного агента.
